# ros2_data_collect

> 이기종 센서 동기 수집 플랫폼

서로 다른 장치에서 서로 다른 주기로 생성되는 센서 스트림을 하나의 시간축으로 정렬하고,
재현 가능한 형태로 기록한다.

인식 모델이 아니라 수집 인프라를 만든다. 시각 정렬이 어긋난 데이터는 어떤 모델로도 복구할 수 없으므로, "정렬의 정확도를 측정 가능한 수치로 보증하는 것"을 최우선 목표로 삼았다.

---

## 1. 목표와 요구사항

### 1.1 최종 목표 시스템과의 대응

DMS(운전자 모니터링) 환경은 RGB-D·IR 카메라, 레이더, 웨어러블을 쓴다. 보유 장비로 동일한 구조를 축소 구현하고, 센서 종류에 의존하는 부분을 인터페이스 뒤로 격리했다.

| 목표 시스템 | 본 프로젝트 | 공유하는 기술 과제 |
|---|---|---|
| RGB-D / IR 카메라 | 노트북 웹캠 | 프레임 타임스탬프, 드롭 검출 |
| 차량 내 마이크 어레이 | 블루투스 이어폰 마이크 | 오디오 청크 경계와 영상 정렬 |
| 웨어러블 생체신호 | 안드로이드 폰 IMU | 무선 전송, 독립 클럭 보정 |
| 레이더 | (미보유) | 인터페이스만 정의 |

### 1.2 요구사항과 충족 여부

| ID | 요구사항 | 수용 기준 | 상태 |
|---|---|---|---|
| FR-1 | 이기종 스트림을 ROS2 토픽으로 수집 | 영상·오디오·IMU 동시 발행 | **부분** — 영상·오디오만 |
| FR-2 | 각 샘플에 **취득 시각** 부여 | 발행 시각이 아닌 캡처 시각이 헤더에 | **완료** |
| FR-3 | 독립 클럭 장치의 시각 보정 | 폰 타임스탬프가 ROS 시간축으로 변환 | 미구현 |
| FR-4 | 근접 시각 샘플을 묶어 정렬 스트림 생성 | 허용오차 내 샘플이 하나로 발행 | 미구현 |
| FR-5 | 세션 단위 기록 | 세션 디렉터리에 rosbag2 + 메타데이터 | **부분** — bag만 (CLI) |
| FR-6 | 수집 조건을 메타데이터로 기록 | 센서 사양·샘플레이트·오프셋 기록 | 미구현 |
| FR-7 | 센서 상태 실시간 관측 | 토픽별 실측 Hz·드롭 수 발행 | **부분** — 브리지 리포트 |
| FR-8 | 단일 명령으로 기동 | launch 파일 하나 | **완료** |
| FR-9 | 기록 데이터 무결성 검증 | 결측·시각 역전·드롭 보고 | 미구현 |

| 비기능 요구사항 | 목표 | 실측 |
|---|---|---|
| 영상 드롭률 | 1% 미만 | **0.11%** (충족) |
| 오디오 드롭률 | 0% | **0%** (충족) |
| **동기화 정확도** | **50ms 이내** | **185.8 ~ 272.2ms — 미충족** (§5.2) |


### 1.3 제약과 그로 인한 설계 결정

| 제약 | 원인 | 대응 |
|---|---|---|
| WSL2에서 노트북 카메라·블루투스 오디오 접근 불가 | WSL2 커널에 UVC/BT 스택 미포함 | 캡처를 Windows 네이티브 프로세스에 두고 소켓으로 전달 |
| 폰과 PC의 클럭이 다름 | 물리적으로 분리된 장치 | 왕복 측정 기반 오프셋 보정 (미구현) |

제약을 우회한 결과가 오히려 설계를 개선했다. 카메라·마이크·폰이 모두 "외부 프로세스 →
브리지 노드 → 토픽"이라는 동일 경로를 따르게 되어 시스템이 하나의 패턴으로 설명되고,
실제 차량에서 센서가 별도 제어 장치에 붙는 구성과도 대응된다.

## 2. 시스템 구조

```text
┌─ Windows (호스트) ──────────────────────┐
│  capture_bridge.py                      │
│   ├ VideoCapturer  ─ OpenCV ─ 웹캠       │
│   ├ AudioCapturer  ─ sounddevice ─ 마이크 │
│   └ FrameSender    ─ 큐 + 송신 스레드     │
└────────────────┬────────────────────────┘
                 │ TCP (길이 프리픽스 프레이밍, port 5555)
                 ▼
┌─ WSL2 / Ubuntu 22.04 / ROS 2 Humble ─────────────────────────┐
│  host_bridge_node                                             │
│   ├ 수신 스레드 ─ FrameQueue (영상/오디오 분리)                  │
│   └ 타이머 콜백 ─┬─> /sensors/camera/image_raw/compressed      │
│                 └─> /sensors/audio/chunk                      │
│                                                               │
│  (예정) sync_node ─> /session/synced,  recorder_node ─> bag    │
└───────────────────────────────────────────────────────────────┘
```

### 2.1 계층 분리

1. **캡처** — 장치 고유 API에 의존. 장비 교체의 영향을 받는 유일한 계층.
2. **브리지** — 바이트열을 ROS2 메시지로 변환.
   > 여기서 발행되는 모든 메시지의 `header.stamp`는 ROS 시간축의 **취득 시각**이다. 발행 시각이 아니다.
3. **처리** — 정렬·기록·감시. 센서가 무엇인지 모른 채 타임스탬프만 다룬다.

상위 계층 전체가 브리지의 사후 조건 위에서만 동작하므로, 센서 추가는 퍼블리셔 노드
추가와 launch 등록으로 끝난다.

### 2.2 토픽과 QoS

| 토픽 | 타입 | 주기 | QoS | 근거 |
|---|---|---|---|---|
| `/sensors/camera/image_raw/compressed` | `sensor_msgs/CompressedImage` | 30Hz | BEST_EFFORT, depth 5 | 프레임이 독립적·대용량. 재전송보다 최신 프레임이 낫다 |
| `/sensors/audio/chunk` | `data_collect_msgs/AudioChunk` | 31.25Hz | RELIABLE, depth 10 | 연속 신호. 한 청크 유실이 파형에 구멍을 낸다 |
| `/sync/clock_offset` | `data_collect_msgs/ClockOffset` | 1Hz | RELIABLE, TRANSIENT_LOCAL | 늦게 뜬 노드도 마지막 오프셋을 즉시 받아야 한다 |

### 2.3 전송 프로토콜

```text
헤더 (빅 엔디안, 21바이트)
  payload_len   uint32
  message_type  uint8
  timestamp_ns  int64     데이터 취득 시각 (발행 시각 아님)
  seq           int64     데이터 종류별 독립 시퀀스

오디오 서브헤더 (빅 엔디안, 10바이트)
  frame_rate uint32 / channels uint16 / frame_count uint32
  ---- 이하 PCM: 리틀 엔디안 int16 ----
```

헤더는 빅 엔디안으로 명시하고 PCM 본문은 리틀 엔디안으로 고정했다. 

수신 측은 `array.array('h')`로 읽는데 이 모듈에는 엔디안 지정 타입코드가 없다. 네이티브로
읽은 뒤 `sys.byteorder`로 판별해 필요 시 `byteswap`한다. x86에서는 실행되지 않는 분기지만,
빅 엔디안 기기에서 이 줄이 없으면 예외도 로그도 없이 잡음이 기록된다.

`MAX_PAYLOAD = 1MB` 상한은 프레이밍이 깨졌을 때 쓰레기 길이값으로 대용량 할당을 시도하다
프로세스가 죽는 것을 막는다.

## 3. 실행 방법

| 항목 | 값 |
|---|---|
| OS | Ubuntu 22.04 (WSL2) / 호스트 Windows 11 |
| ROS | ROS 2 Humble, Python 3.10 |
| 카메라 | 노트북 웹캠, 640×480 MJPG |
| 마이크 | 블루투스 이어폰 (WASAPI, 16kHz 모노) |

> **WSL 주의.** pip으로 설치된 NumPy 2.x가 있으면 apt의 `cv2`(1.x 링크)가 임포트 단계에서
> 깨진다. pip NumPy를 삭제하거나 `pip3 install "numpy<2"`로 내린다.

### 3.1 빌드

```bash
cd ~/ros2_data_collect
colcon build --packages-select data_collect_msgs data_collect
source install/setup.bash
```

### 3.2 Windows 측 준비

```powershell
pip install opencv-python sounddevice numpy
python data_capture\print_device.py
```

입력 채널을 제공하는 장치 목록이 출력된다. 여기서 마이크를 하나 고른다.
**MME API 장치는 ADC 취득 시각을 제공하지 않는 경우가 많으므로 지양한다.**

장치 번호는 재부팅·재연결 시 바뀌므로 이름으로 찾는다. `capture_bridge.py`의 `main`에서
아래 인자를 수정한다 (예: `"buds2", "WASAPI"`).

```python
audio_capturer = AudioCapturer(frame_sender, device=find_input_device("디바이스명", "API명"))
```

### 3.3 기동과 확인

TCP 서버가 수신 측이므로 `host_bridge`를 먼저 띄운다.

```bash
ros2 launch data_collect data_collect.launch.py
```

```powershell
python data_capture\capture_bridge.py
```

```bash
ros2 topic hz /sensors/camera/image_raw/compressed   # 30
ros2 topic hz /sensors/audio/chunk                   # 31.25
```

### 3.4 기록·재생·분석

```bash
ros2 bag record -o sessions/$(date +%Y-%m-%d_%H%M%S) \
  /sensors/camera/image_raw/compressed /sensors/audio/chunk

ros2 bag play sessions/<디렉터리>
ros2 run rqt_image_view rqt_image_view

python3 scripts/analyze_clap.py sessions/<디렉터리>   # 동기화 정확도 측정
```

## 4. 수집 성능

30초 세션 (`capture_bridge.py` 종료 시 요약).

```text
=== 수집 요약 ===
영상  : 캡처 920, 전송 919, 유실 1(0.11%), 구간 30.6초, 평균 30.03Hz
오디오: 캡처 1200, 전송 1200, 유실 0(0.00%), 구간 38.4초, 평균 31.23Hz
시작 시각 차: 영상이 오디오보다 +7.8초
  영상버림: 0    오디오넘침: 0    캡처실패: 0    status: 0    ADC무효: 0
```

| 항목 | 공칭 | 실측 |
|---|---|---|
| 영상 | 30Hz | 30.03Hz, 유실 0.11% |
| 오디오 | 31.25Hz | 31.23Hz, 유실 0% |
| 대역폭 | — | 약 1MB/s |

수신 측 발행 수가 영상 919 / 오디오 1200으로 **전송 수와 정확히 일치**했고 seq 결번은 0이었다.
소켓 구간 무손실을 양쪽 계수기의 대조로 확인했다.

> 유실 1은 종료 처리 순서에서 온다. `drain()`이 송신 스레드를 조인한 뒤에도 캡처 스레드가
> 살아 있어 마지막 한 장이 큐에 남는다. `영상버림=0`·`캡처실패=0`이 다른 원인을 배제한다.

## 5. 동기화 정확도

### 5.1 방법

카메라 앞에서 3초 간격으로 20회 박수를 치고 bag에 기록한다. 박수 한 번이 두 스트림 모두에
뚜렷한 이벤트를 남기므로, 각 스트림에서 검출한 이벤트의 `header.stamp` 차이가 곧 동기화
오차다. 분석은 `scripts/analyze_clap.py`를 통해 수행.

| 스트림 | 이벤트 검출 |
|---|---|
| 영상 | 프레임 차분이 **급격히 꺾이는 지점** (`stop`) — 접촉하면 움직임이 멎는다 |
| 오디오 | 단시간 에너지의 최대점 |

> 이 시험은 **호스트 클럭 오프셋(§6.2)에 면역이다.** 영상·오디오 타임스탬프가 모두 Windows의
> 같은 시계에서 나오므로, 공통 편향은 차이에서 상쇄된다.

### 5.2 결과 — 요구사항 미충족

한 번의 측정으로는 동기화 오차가 어디서 왔는지 알 수 없으므로, 변수를 하나씩만 바꿔 네 번 측정했다. 마이크 API는 전부 WASAPI로 고정했다.

| 마이크 | 영상 검출 | 평균 편향 | σ | 표본 |
|---|---|---|---|---|
| Galaxy Buds2 Pro (블루투스, 16kHz) | peak | -272.2ms | 12.7ms | 17 |
| Galaxy Buds2 Pro (블루투스, 16kHz) | **stop** | -235.8ms | 12.5ms | 17 |
| 내장 마이크 배열 (유선, 48kHz) | peak | -206.6ms | 10.2ms | 7 |
| 내장 마이크 배열 (유선, 48kHz) | **stop** | **-185.8ms** | **9.2ms** | 7 |

음수는 오디오 타임스탬프가 영상보다 늦다는 뜻이다.

**동기화 정확도 50ms 요구사항은 충족하지 못했다.** 보정 없는 현재 상태에서 영상과 오디오의
타임스탬프는 185.8~272.2ms 어긋난다.

### 5.3 편향의 분해

측정 조건을 하나씩 바꿔 -272.2ms를 두 성분으로 분해했다.

| 성분 | 크기 | 분리 방법 |
|---|---|---|
| 영상 검출 정의 | 36.4ms | 같은 bag에서 검출 정의만 교체 (272.2 → 235.8) |
| 블루투스 무선 링크 | 50.0ms | API 고정, 마이크만 교체 (235.8 → 185.8) |
| 잔여 | 185.8ms | *미분해* |
| **합계** | **272.2ms** | |

**프레임 차분의 최대점(peak)은 손이 맞닿는 순간이 아니라 가장 빠르게 움직이는 순간이다.** 
영상 검출 시점 정의를 stop으로 바꾸자 평균이 프레임 간격(33.3ms) 수준만큼 0 쪽으로 이동했고 **σ는 12.7 → 12.5ms로 변하지
않았다.** 같은 bag·같은 17쌍이므로 이 차이는 검출 정의에만 귀속된다.

남은 185.8ms의 원인 후보는 다음과 같다.

| 잔여분 후보 | 분리 방법 |
|---|---|
| WASAPI 공유 모드 버퍼링 | 배타 모드 또는 WDM-KS와 비교 |
| 입력 DSP (빔포밍·잡음억제) | DSP 비활성 장치와 비교 |
| `inputBufferAdcTime`이 드라이버 버퍼를 반영하지 않을 가능성 | 알려진 지연의 기준 신호와 비교 |


### 5.4 지터가 뜻하는 것

σ가 9.2~12.7ms에 불과하다는 것은 오차의 대부분이 무작위가 아니라 구성별 상수라는 뜻이다.
상수는 측정해서 빼면 없어지고, 보정 후 남는 오차의 상한이 σ이므로, **보정을 구현하면 50ms 요구사항을 충족할 수 있다.**

### 5.5 방법론 상 확인한 것

이벤트 매칭 허용 시간차를 넓히면 표본이 늘지만, 오검출이 멀리 떨어진 이벤트에 잘못 붙는다.

| 조건 | 최대 시간차 | 표본 | σ |
|---|---|---|---|
| 블루투스, peak | 0.5초 | 17 | 12.7ms |
| 블루투스, peak | 1.0초 | 20 | **221.9ms** |
| 유선, stop | 0.5초 | 8 | **72.3ms** |
| 유선, stop | 0.3초 | 7 | 9.2ms |

## 6. 측정에서 드러난 문제

### 6.1 소스별 시간축

초기 요약은 오디오를 34.24Hz로 보고했다. 공칭 31.25Hz보다 9.5% 빠른 값이라 장치를
의심했으나, `ros2 topic hz`는 31.25Hz를 보였다.

**틀린 것은 분모였다.** 카메라 준비 완료 이후의 경과 시간으로 모든 소스를 나누고 있었는데,
블루투스 마이크가 먼저 준비되어 캡처를 시작한 구간이 빠져 있었다.

```text
2690 ÷ 31.25 = 86.1초   오디오가 실제로 돌아간 시간
                78.6초   요약이 쓴 시간 (영상 기준)
                 7.5초   차이 → 234개 ≈ 오차의 전부
```

소스별로 첫·마지막 취득 시각을 기록해 각자의 구간으로 나누도록 고쳤다.

```python
평균 Hz = (표본 수 - 1) / (마지막 취득 시각 - 첫 취득 시각)
```

시작 시각 차 7.8초는 버그가 아니라 기록해야 할 사실이다. `sync_node`는 두 소스가 겹치는
구간에서만 짝을 만들 수 있으므로 묶임 성공률의 상한이 여기서 정해진다.

### 6.2 클럭 오프셋

같은 PC이므로 시계도 같으리라 가정했으나 WSL2와 Windows는 별개의 시계를 가진다.

| 상태 | 캡처 → 수신 지연 |
|---|---|
| 보정 전 | **-0.25초** (음수 = 미래에서 온 타임스탬프) |
| `hwclock -s` 후 | 평균 35ms, 최솟값은 여전히 음수 |

절전 모드 복귀 시 재발한다. **클럭 보정은 폰 전용 기능이 아니라 호스트 브리지에도
필요하다**는 것이 이 측정의 결론이다.

## 7. 설계 결정과 근거

### 7.1 메시지 대입이 55ms 걸리는 문제 해결 — `array.array`

`msg.data`에 921,600바이트를 넣는 데 **약 55ms**가 걸려 프레임 주기 33ms를 넘어섰다.
(참고로 JPEG 디코딩은 약 2ms로, 병목은 디코딩이 아니었다.)

ROS 메시지 필드는 속성 대입이 오버로드되어 있고, rclpy의 setter는 **원소를 전수 검사**한다.
그런데 검사에 앞서 `array.array` 여부를 확인하는 빠른 경로가 있다.

```python
message.data = frame.payload                     # bytes → 원소 전수 검사
message.data = array.array('B', frame.payload)   # 빠른 경로로 검사 우회
```

오디오 경로에서도 같은 이유로 `array.array('h')`를 쓴다.

### 7.2 영상 토픽 발행률이 낮은 문제 해결 — `CompressedImage`

`sensor_msgs/Image`로 원본 프레임을 발행하자 **30프레임 중 6프레임만 도달**했다. 브리지는
정상적으로 발행하고 있었으므로 원인은 발행 이후, **토픽 수신 버퍼가 넘친 것으로 추정된다.**

```text
640 × 480 × 3 바이트 × 30fps ≈ 27MB/s
```

JPEG을 디코딩하지 않고 `CompressedImage`로 그대로 실어 보내 해결했다. 대역폭이 약
27MB/s에서 **1MB/s로 줄었고** 도달률이 100%가 됐다.

### 7.3 캡처와 전송의 분리

캡처 직후 소켓에 쓰면 네트워크가 밀릴 때 캡처 주기가 함께 밀린다. 캡처 스레드는 큐에
넣기만 하고 별도 송신 스레드가 비운다. **큐 정책은 스트림 성질에 따라 다르다.**

| | 상한 | 
|---|---|
| 영상 | 60 |
| 오디오 | 공용 큐 400 |

한 큐를 공유하되 영상 점유 상한을 따로 두어 **큐가 영상으로 가득 차서 오디오가 밀리는
상황**을 막는다. RELIABLE QoS로 오디오를 보호해도 그 앞단에서 버려지면 의미가 없다.
수신 측에선 `FrameQueue`에서 영상 30 / 오디오 400으로 큐를 분리했다.

수신 측 타이머 콜백은 **틱당 한 개만 꺼내 반환을 보장한다.** `while` 루프로 비우면 유입이
빠를 때 콜백이 반환하지 않아 리포트 타이머가 굶는다.

### 7.4 시퀀스 번호의 역할

TCP는 순서와 전달을 보장하므로 결번은 정상적으로는 발생하지 않는다. seq는 유실이 아니라
프레이밍을 검증한다. 직접 만든 길이 프리픽스 프레이밍에서 송·수신이 한 바이트라도
어긋나면 그 뒤 전체가 쓰레기로 해석된다.

```text
seq 결번        프레이밍 층
JPEG/청크 오류   내용 층
send_error      소켓 층
```

계수기를 층별로 나눴기에 어느 것이 오르는지만 보고 의심할 곳을 좁힐 수 있다.

 **UDP에서는 의미가 달라진다.** `sendto`는 패킷이 사라져도 성공을 반환하므로 seq 결번이
 유일한 판정 수단이 된다. 또한 재정렬·중복이 정상 동작이라 현재의 "기대값보다 크면 결번"
 방식은 재정렬을 유실로 오인한다. IMU 도입 시 `유실 = (max_seq - min_seq + 1) - 수신 개수`
 같은 순서 무관 방식으로 바꿔야 한다.

### 7.5 오디오 타임스탬프

`header.stamp`는 **청크 첫 샘플이 ADC를 통과한 시각**이다. 콜백 호출 시각을 쓰면 블록
길이(512샘플 = 32ms)만큼 밀린다.

```python
first_sample_age = time_info.currentTime - time_info.inputBufferAdcTime
timestamp_ns = now_ns - int(first_sample_age * 1e9)
```

`inputBufferAdcTime`이 0을 반환하는 백엔드가 있어 폴백을 두었으나, 사용 중인 장치는
유효값을 제공하였다.
