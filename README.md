# ros2_data_collect

> 이기종 센서 동기 수집 플랫폼

서로 다른 장치에서 서로 다른 주기로 생성되는 센서 스트림을 하나의 시간축으로 정렬하고, 재현 가능한 형태로 기록하는 것이 목표이다.

이 프로젝트는 인식 모델이 아니라 수집 인프라를 만든다. 시각 정렬이 어긋난 데이터는 어떤 모델로도 복구할 수 없으므로, "정렬의 정확도를 측정 가능한 수치로 보증하는 것"을 최우선 목표로 삼았다.

## 3. 실행 방법

### 3.1 빌드

```bash
cd ~/ros2_data_collect
colcon build --packages-select data_collect_msgs data_collect
source install/setup.bash
```

### 3.2 Windows 측 준비

WSL2 커널에는 UVC 드라이버가 없어 웹캠에 직접 접근할 수 없고, 블루투스 오디오 스택도 없다. 따라서 캡처는 Windows 네이티브 프로세스가 담당한다.

먼저 다음 패키지를 설치한다.
```powershell
pip install opencv-python sounddevice numpy
```

다음으로 사용할 수 있는 마이크 목록을 다음 스크립트를 실행하여 확인한다.

```powershell
python data_capture\print_device.py
```

이 스크립트는 입력 채널을 제공하는 장치 목록을 출력한다. 목록 중 오디오 데이터 수집에 사용할 기기를 하나 선택한다. MME API를 사용하는 장치는 ADC 수집 시각을 제공하지 않는 경우가 많으므로 지양한다.

장치 번호는 재부팅/재연결 시 바뀌므로, capture_bridge.py의 find_input_device 함수를 사용해 이름 일부 및 API로 찾는다. capture_bridge.py의 main 함수에서
```python
audio_capturer = AudioCapturer(frame_sender, device=find_input_device("디바이스명", "API명"))
```
행의 `"디바이스명", "API명"` 부분을 적절히 수정할 것. 예: `"buds2", "WASAPI"`

### 3.3 기동

TCP 서버가 수신 측이므로 `host_bridge`를 먼저 띄운다.

```bash
ros2 launch data_collect data_collect.launch.py
```

```powershell
python data_capture\capture_bridge.py
```

### 3.4 확인

```bash
ros2 topic hz /sensors/camera/image_raw/compressed   # 30
ros2 topic hz /sensors/audio/chunk                   # 31.25
```

### 3.5 기록·재생

```bash
ros2 bag record -o sessions/$(date +%Y-%m-%d_%H%M%S) \
  /sensors/camera/image_raw/compressed /sensors/audio/chunk

ros2 bag play sessions/<디렉터리>
ros2 run rqt_image_view rqt_image_view
```

## 4. 시스템 구조

```text
┌─ Windows (호스트) ──────────────────────┐
│  capture_bridge.py                      │
│   ├ VideoCapturer  ─ OpenCV ─ 웹캠       │
│   ├ AudioCapturer  ─ sounddevice ─ 마이크 │
│   └ FrameSender    ─ 큐 + 송신 스레드     │
└────────────────┬────────────────────────┘
                 │ TCP (길이 프리픽스 프레이밍, port 5555)
                 ▼
┌─ WSL2 / Ubuntu 22.04 / ROS 2 Humble ─────────────────────────┐
│  host_bridge_node                                             │
│   ├ 수신 스레드 ─ FrameQueue (영상/오디오 분리)                  │
│   └ 타이머 콜백 ─┬─> /sensors/camera/image_raw/compressed      │
│                 └─> /sensors/audio/chunk                      │
│                                                               │
│  (예정) sync_node      ─> /session/synced                      │
│  (예정) recorder_node  ─> rosbag2 + session.yaml               │
└───────────────────────────────────────────────────────────────┘
```

### 4.1 계층 분리

1. 캡처 계층: 장치 고유 API에 의존한다. 장비 교체의 영향을 받는 유일한 계층이다.
1. 브리지 계층: 바이트열을 ROS2 메시지로 변환한다. 이 계층은 단 하나의 사후 조건을 보장한다.
    * 발행되는 모든 메시지의 `header.stamp`는 ROS 시간축의 취득 시각이다. 발행 시각이 아니다.
1. 처리 계층: 정렬·기록·감시. 센서가 무엇인지 모른 채 타임스탬프만 다룬다.

카메라·마이크·(예정된) 폰이 모두 "외부 프로세스 → 브리지 노드 → 토픽"이라는 동일 경로를 따른다.

### 4.2 토픽

| 토픽 | 타입 | 주기 | QoS | 근거 |
|---|---|---|---|---|
| `/sensors/camera/image_raw/compressed` | `sensor_msgs/CompressedImage` | 30Hz | BEST_EFFORT, depth 5 | 프레임이 독립적·대용량. 재전송보다 최신 프레임이 낫다 |
| `/sensors/audio/chunk` | `data_collect_msgs/AudioChunk` | 31.25Hz | RELIABLE, depth 10 | 연속 신호. 한 청크 유실이 파형에 구멍을 낸다 |
| `/sync/clock_offset` | `data_collect_msgs/ClockOffset` | 1Hz | RELIABLE, TRANSIENT_LOCAL | 늦게 뜬 노드도 마지막 오프셋을 즉시 받아야 한다 |

**QoS는 스트림의 성질에서 도출했다.** 영상과 오디오에 같은 정책을 쓰면 한쪽이 반드시 손해를 본다.

### 4.3 전송 프로토콜

```text
헤더 (빅 엔디안, 21바이트)
  payload_len   uint32
  message_type  uint8
  timestamp_ns  int64     데이터 취득 시각 (발행 시각 아님)
  seq           int64     데이터 종류별 독립 시퀀스

오디오 서브헤더 (빅 엔디안, 10바이트)
  frame_rate    uint32
  channels      uint16
  frame_count   uint32
  ---- 이하 PCM: 리틀 엔디안 int16 ----
```

헤더는 빅 엔디안, PCM 본문은 리틀 엔디안으로 고정했다.

수신 측은 `array.array('h')`로 읽는데 이 모듈에는 엔디안 지정 타입코드가 없다. 따라서 네이티브로 읽은 뒤 `sys.byteorder`로 판별해 필요 시 `byteswap`한다. x86 환경에서는 실행되지 않는 분기지만, 빅 엔디안 기기에서 이 줄이 없으면 예외도 로그도 없이 잡음이 기록된다.

`MAX_PAYLOAD = 1MB` 상한은, 프레이밍이 깨졌을 때 쓰레기값으로 대용량 할당을 시도하다 프로세스가 죽는 것을 막는다.

## 5. 실측 결과

### 5.1 수집 성능

30초 세션 기준 (`capture_bridge.py` 종료 시 요약).

```text
=== 수집 요약 ===
영상  : 캡처 920, 전송 919, 유실 1(0.11%), 구간 30.6초, 평균 30.03Hz
오디오: 캡처 1200, 전송 1200, 유실 0(0.00%), 구간 38.4초, 평균 31.23Hz
시작 시각 차: 영상이 오디오보다 +7.8초
  영상버림: 0    오디오넘침: 0    캡처실패: 0    status: 0    ADC무효: 0
```

수신 측(`host_bridge`)의 발행 수는 영상 919 / 오디오 1200으로 전송 수와 정확히 일치했고,
seq 결번은 0이었다. 소켓 구간에서 잃은 데이터가 없음을 양쪽 계수기의 대조로 확인했다.

| 항목 | 공칭 | 실측 |
|---|---|---|
| 영상 | 30Hz | 30.03Hz |
| 오디오 | 31.25Hz | 31.23Hz |
| 영상 유실률 | < 1% | 0.11% (종료 시 꼬리 1프레임) |
| 오디오 유실률 | 0% | 0% |
| 대역폭 | — | 약 1MB/s |

> 영상 유실률 0.11%는 종료 처리 순서에서 온다. 
>`drain()`이 송신 스레드를 조인한 뒤에도 캡처 스레드가 살아 있어, 마지막 한 장이 큐에 남는다. 
>`영상버림=0`·`캡처실패=0`이 다른 원인을 배제한다.

### 5.2 소스별 시간축 — 측정에서 드러난 문제

초기 요약은 오디오를 34.24Hz로 보고했다. 공칭 31.25Hz보다 9.5% 빠른 값이라 장치가
`blocksize`나 샘플레이트를 지키지 않는 것을 의심했으나, `ros2 topic hz`는 31.25Hz를 보였다.

틀린 것은 분모였다. 초기 Hz 계산 코드는 카메라 캡처 프로세스 준비 완료 이후 경과 시간으로, 각 소스의 캡처 성공 횟수를 나누고 있었다. 그러나 블루투스 마이크가 카메라보다 먼저 준비되어 캡처를 수행하고 있었고, 그 구간이 경과 시간에서 빠져 있었다.

```text
2690 ÷ 31.25 = 86.1초   오디오 캡처가 실제로 돌아간 시간
                78.6초   요약이 쓴 시간 (영상 기준)
                 7.5초   오디오만 먼저 시작한 구간 → 234개 ≈ 차이의 전부
```

소스별로 첫·마지막 취득 시각을 기록해 각자의 구간으로 나누도록 고쳤다.

```python
평균 Hz = (표본 수 - 1) / (마지막 취득 시각 - 첫 취득 시각)
```

시작 시각 차 7.8초는 버그가 아니라 기록해야 할 사실이다. `sync_node`는 두 소스가 겹치는 구간에서만 짝을 만들 수 있으므로 묶임 성공률의 상한이 여기서 정해진다.

### 5.3 클럭 오프셋

WSL2와 Windows는 별개의 시계를 가진다. 같은 PC이므로 시계도 같으리라 가정했으나 실측
결과가 달랐다.

| 상태 | 캡처 시각 → 수신 시각 지연 |
|---|---|
| 보정 전 | **-0.25초** (음수 = 미래에서 온 타임스탬프) |
| `hwclock -s` 후 | 평균 35ms, 최솟값은 여전히 음수 |

절전 모드 복귀 시 오프셋이 다시 발생한다. 
클럭 보정은 폰 전용 기능이 아니라 호스트 브리지에도 필요하다는 것이 이 측정의 결론이다.

### 5.4 동기화 정확도 (박수 시험)

카메라 앞에서 3초 간격으로 20회 박수를 치고 bag에 기록했다. 
박수 한 번이 두 스트림 모두에 뚜렷한 이벤트를 남기므로, 각 스트림에서 검출한 이벤트의 `header.stamp` 차이가 곧 동기화 오차다. 
분석을 위해 scripts/analyze_clap.py 스크립트를 사용했다.

첫 번째 분석에서 평균 편향이 -272.2ms로 계산되었다. 타임스탬프 차이가 무엇으로부터 왔는지 규명하기 위해, 두 변수를 하나씩만 바꿔 총 네 번
측정했다.

| 마이크 | 영상 검출 | 평균 편향 | 표준편차 | 표본 | 검출 |
|---|---|---|---|---|---|
| Galaxy Buds2 Pro (블루투스, 16kHz) | peak | -272.2ms | 12.7ms | 17 | 영상 20 / 오디오 20 |
| Galaxy Buds2 Pro (블루투스, 16kHz) | **stop** | **-235.8ms** | **12.5ms** | 17 | 영상 20 / 오디오 20 |
| 내장 마이크 배열 (유선, 48kHz) | peak | -206.6ms | 10.2ms | 7 | 영상 20 / 오디오 17 |
| 내장 마이크 배열 (유선, 48kHz) | **stop** | **-185.8ms** | **9.2ms** | 7 | 영상 20 / 오디오 17 |

음수는 오디오 타임스탬프가 영상보다 늦다는 뜻이다. `peak`는 영상 이벤트를 프레임 차분의 최대점으로 잡았음을 의미하며, `stop`은 움직임이 멎는 지점을 영상 이벤트로 잡았음을 의미한다.(아래 참조).

#### 지터 — 목표를 판정하는 값


#### 편향 원인 파악

측정 조건을 하나씩 바꿔 -272.2ms(블루투스, peak) 중 두 성분을 분리했다.

| 성분 | 크기 | 분리 방법 |
|---|---|---|
| 블루투스 무선 링크 | **50.0ms** | API 고정, 마이크만 교체 (235.8 → 185.8) |
| 잔여 — 오디오 경로 | 185.8ms | *미분해* |

그리고 측정 방법 자체의 편향을 별도로 확인했다.

| 성분 | 크기 | 분리 방법 |
|---|---|---|
| 영상 검출 정의 | 블루투스 **36.4ms** / 유선 **20.8ms** | 같은 bag에서 검출 정의만 교체 |

**프레임 차분의 최대점은 손이 맞닿는 순간이 아니라 가장 빠르게 움직이는 순간이다.**
접촉하면 움직임이 멎으므로, 최대점 이후 하강이 가장 가파른 지점이 접촉에 해당한다.
정의를 바꾸자 평균이 프레임 간격(33.3ms) 수준만큼 0 쪽으로 이동했고 **σ는 12.7 → 12.5ms로
변하지 않았다.** 같은 bag·같은 17쌍이므로 이 차이는 검출 정의에만 귀속된다.

#### 남은 185.8ms

**오디오 경로의 편향이다.** 카메라 파이프라인 지연은 영상 타임스탬프를 *늦게* 만들어
편차를 양수 쪽으로 밀므로 음수 편차를 설명할 수 없다. 남은 후보는 셋이며 현재 장비로는
분리할 수 없다.

| 후보 | 분리 방법 |
|---|---|
| WASAPI 공유 모드 버퍼링 | 배타 모드 또는 WDM-KS와 비교 |
| 입력 DSP (인텔 스마트 사운드의 빔포밍·잡음억제) | DSP 비활성 장치와 비교 |
| `inputBufferAdcTime`의 의미 — 드라이버 버퍼를 반영하지 않을 수 있다 | 알려진 지연의 기준 신호와 비교 |

**분해되지 않은 채로 기록한다.** 원인을 특정하지 않은 것이 특정한 척하는 것보다 낫다.

#### 방법론 상 확인한 것

**표본 수를 늘리는 것이 항상 개선은 아니다.** 이벤트 짝짓기 허용 시간차(`--max-gap`)를
넓히면 표본이 늘지만 오검출이 멀리 떨어진 이벤트에 잘못 붙는다.

| 조건 | 게이트 | 표본 | σ |
|---|---|---|---|
| 블루투스, peak | 0.5초 | 17 | 12.7ms |
| 블루투스, peak | 1.0초 | 20 | **221.9ms** |
| 유선, stop | 0.5초 | 8 | **72.3ms** |
| 유선, stop | 0.3초 | 7 | 9.2ms |

늘어난 표본은 박수가 아닌 움직임의 오검출이었다. **짝짓기 실패는 결함이 아니라 필터가
작동한 결과이므로, 검출 수와 짝 수를 항상 함께 보고한다.**

내장 마이크는 잡음억제·AGC가 박수 크기를 눌러 검출률이 낮았다(오디오 17/20).

> 이 시험은 **호스트 클럭 오프셋(§5.3)에 면역이다.** 영상·오디오 타임스탬프가 모두 Windows의
> 같은 시계에서 나오므로 공통 편향은 차이에서 상쇄된다. 260ms와 크기가 비슷한 것은 우연이다.

## 6. 설계 결정과 근거

### 6.1 `Image` → `CompressedImage`

설계서는 `cv_bridge`로 JPEG을 디코딩해 `sensor_msgs/Image`로 발행하도록 했으나,
**30프레임 중 6프레임만 도달**했다.

측정한 비용은 다음과 같다.

| 단계 | 소요 |
|---|---|
| JPEG 디코딩 | 약 2ms |
| `msg.data = <921,600바이트>` 대입 | **약 55ms** |

병목은 디코딩이 아니라 대입이었다. rclpy는 시퀀스 필드에 값을 넣을 때 **원소를 전수
검사**하므로, 640×480×3 바이트를 넣는 순간 프레임 주기(33ms)를 넘어선다.

JPEG을 그대로 실어 보내면 디코딩도 대입 비용도 사라진다.

```python
message.data = array.array('B', frame.payload)   # uint8[], 전수 검사 우회
```

**부수 효과가 더 컸다.** `host_bridge`에서 NumPy와 OpenCV 의존이 사라져 WSL 쪽 pip 충돌
위험이 없어졌고, 대역폭이 약 27MB/s에서 1MB/s로 줄었다. 압축 해제는 소비자가 필요할 때만
하면 되므로 수집 단계에서 할 이유가 없다.

### 6.2 캡처와 전송의 분리

캡처 직후 소켓에 쓰면 네트워크가 밀릴 때 캡처 주기가 함께 밀린다. 캡처 스레드는 큐에
넣기만 하고 별도 송신 스레드가 큐를 비운다.

**큐 정책은 스트림 성질에 따라 다르다.**

| | 상한 | 넘칠 때 |
|---|---|---|
| 영상 | 60 | 버린다 (최신 프레임이 중요) |
| 오디오 | 공용 큐 400 | 버리면 파형에 구멍. 여기가 차면 이미 비정상 |

한 큐를 공유하되 영상 점유 상한을 따로 두어, **큐가 영상으로 가득 차서 오디오가 밀리는
상황**을 막는다. RELIABLE QoS로 오디오를 보호해도 그 앞단에서 버려지면 의미가 없다.

수신 측도 같은 이유로 `FrameQueue`에서 영상 30 / 오디오 400으로 분리했다.

### 6.3 타이머 콜백의 반환 보장

수신 측 타이머 콜백이 `while` 루프로 큐를 비우면, 유입이 빠를 때 콜백이 반환하지 않아
리포트 타이머가 굶는다. 실제로 겪은 문제다.

**틱당 한 개만 꺼내 반환을 보장한다.** 2ms 주기이므로 초당 500개 처리 능력이고, 실제
유입은 두 스트림 합쳐 약 61개라 정상 상태에서 충분하다.

다만 순간적으로 큐가 쌓이면 회복 속도가 이 상한에 묶인다. 오디오 큐 400개가 차면 비우는
데 0.8초가 걸리므로, 넘침이 관측되는데 원인이 분명하지 않다면 여기를 의심한다.

### 6.4 시퀀스 번호의 역할

TCP는 순서와 전달을 보장하므로 seq 결번은 정상적으로는 발생하지 않는다. **seq는 유실이
아니라 프레이밍을 검증한다.**

직접 만든 길이 프리픽스 프레이밍에서 송·수신이 한 바이트라도 어긋나면, 예외 없이 그 뒤
스트림 전체가 쓰레기로 해석된다. 이때 계수기들은 이렇게 움직인다.

```text
송신 오류      없음          보낸 쪽은 문제를 모른다
JPEG오류      급증          내용이 깨진 것처럼 보인다
seq          큰 값으로 점프  ← 프레이밍이다
```

seq가 없으면 `JPEG오류`만 보고 인코딩이나 카메라를 의심하게 된다. 계수기를 층별로 나눈
이유가 여기 있다.

```text
seq 결번        프레이밍 층
JPEG/청크 오류   내용 층
send_error      소켓 층
```

그리고 seq는 **데이터에 실려 오므로 수신 측이 송신 측 계수기를 신뢰하지 않고 검증할 수
있다.** 두 프로세스의 계수기가 어긋날 때 어느 쪽을 믿을지 판정하는 근거가 된다.

> **UDP에서는 의미가 달라진다.** `sendto`는 패킷이 사라져도 성공을 반환하므로 송신 측이
> 유실을 인지할 방법이 원리적으로 없고, seq 결번이 유일한 판정 수단이 된다. 또한 UDP는
> 재정렬과 중복이 정상 동작이므로 현재의 "기대값보다 크면 결번" 방식은 재정렬을 유실로
> 오인한다. IMU 도입 시 순서 무관한 방식으로 바꿔야 한다.
>
> ```text
> 유실 = (max_seq - min_seq + 1) - 수신 개수
> ```

### 6.5 오디오 타임스탬프

`header.stamp`는 **청크 첫 샘플이 ADC를 통과한 시각**이다. 콜백 호출 시각을 쓰면 블록
길이(512샘플 = 32ms)만큼 밀린다.

```python
first_sample_age = time_info.currentTime - time_info.inputBufferAdcTime
timestamp_ns = now_ns - int(first_sample_age * 1e9)
```

`inputBufferAdcTime`이 0을 반환하는 백엔드가 있어 폴백을 두었으나, 사용 중인 장치는
유효값을 제공한다(`ADC무효: 0`). 폴백은 블록 길이만 고려하는 근사이며, 남는 오차는 상수
편향으로 박수 시험에서 실측한다.

## 8. 시행착오 기록

**WSL 2.7.3에서 GUI 창이 뜨지 않음.** `/mnt/shared_memory`가 마운트되지 않아 WSLg가 동작하지
않았다. tmpfs를 수동 마운트해 해결했다.

**NumPy 2.x ↔ cv2 충돌.** pip으로 NumPy를 올리자 apt로 설치된 `cv2`가 임포트 단계에서 깨졌다.
이후 WSL 측은 apt만 사용하는 규칙을 세웠고, §6.1의 `CompressedImage` 전환으로 의존 자체를
제거했다.

**블루투스 마이크와 WDM-KS.** §3.2 참조. 목록에 보이는 장치가 반드시 열리는 것은 아니다.

**오디오 34.24Hz 오보고.** §5.2 참조. 측정 코드의 결함이 센서의 문제로 보였던 사례다.
